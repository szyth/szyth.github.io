How I found 33,000+ users' data and government documents leaking

Feb 26, 20233 min read#pentest#api#idor

All client-specific details (website, APIs, server URLs) have been changed to respect the NDA.

Summary of findings

  • Used a Google dork to find the target's subdomains.
  • Found student.example.com and registered a user there.
  • Intercepting the login API calls revealed the API server (api-server.com).
  • The server's page returned nothing except © 2023 - My ASP.NET Web Secure API.
  • A quick directory fuzz found a /help directory: an API documentation page.
  • The POST getUserDetails() API caught my eye, so I opened its details page.
  • The details page was completely blank. The server did respond with text/html, but nothing showed in the browser.
  • Inspecting the page, I found a global CSS rule set to display: none that hid all the content.
  • Overriding it with display: block revealed the page: the API documentation for getUserDetails().
  • The request body took a user-id integer and an Authorization: Bearer header.
  • I took the login token from the student.example.com account I had registered and sent this request:
curl -i -X POST 'https://api-server.com/getUserDetails' \
  -H 'Authorization: Bearer <Token>' \
  -H 'Content-Type: application/json' \
  -d '{"user-id":"<myuserid>"}'
  • The server returned my user details.
  • Changing the user-id integer returned that user's data too. IDOR, screaming in the background.
  • To show how sensitive the data was, I wrote a multi-threaded IDOR exploitation PoC in Rust to dump it.
  • In total there were 33,000+ users.
  • The data included name, date of birth, email, phone number, address, guardian details and government document filenames, to name a few.

Digging deeper to find the government documents

  • The PII dump only had the documents' filenames, not their path on the server.
  • The next step was finding the directory the server used to serve these files to users after login.
  • Logging back in to student.example.com, I was asked to pay Rs 1000 for registration before I could reach the user profile, where the documents were embedded.
  • Back in the PII dump, I found a user who had already paid.
  • I sent their user ID with a dummy password and proxied the request through Burp Suite.
  • The login failed as expected, but I replaced the proxied response with a success response (copied from my own login).
  • Bingo: the browser logged me in as that user.
  • Their profile showed the government documents and the directory path used to serve them.
  • With that path, a recursive wget over the filenames from the dump could download every document.

Bonus finding

  • The API documentation also listed an updateUserDetails() API.
  • It accepted any valid authorization token together with any user-id.
  • That let me change other users' details in a flick.

Update: these reported findings are now fixed.
