How GitHub recon got me authenticated API access

Jan 17, 20232 min read#pentest#recon#api

I had just finished a web app pentest of one of a client's assets.

It was a black-box engagement with only the in-scope URLs provided: one subdomain and its API endpoints. To respect the NDA, I'll call them dashboard.target.com and api.target.com/v2.

With the scope fixed to a single subdomain, there wasn't much to do in subdomain recon.

GitHub recon

So I turned to GitHub, hoping to find the client's repositories or other useful information.

I tried several search filters and keywords related to dashboard.target.com and api.target.com, but all their repositories were private, so nothing came back.

I broadened the search to public repositories with the same name as the client, and found around 10.

All of them were unfinished, hadn't been touched in a year, and were built with Angular.

Having worked with Angular, I knew environment variables, API endpoints and tokens typically live in environment.*.ts, *.service.ts and *.interceptor.service.ts files.

Two of these repos had a hardcoded API domain and token, though the domain was the development one: api.dev.target.com.

That gave me:

  • The dev API domain
  • An access token
  • API endpoints, extracted from several service.ts files

Does the token still work?

The commits were from 2021, so I expected the token to have expired. I gave it a shot anyway, hit the dev endpoint and, bingo: the API returned data with a 200.

The same token didn't work on the production api.target.com. So the developers had hardcoded the values for development and unknowingly pushed the code to public repositories.

Reporting

Because the finding was on api.dev.target.com, which was out of scope, it couldn't go in the pentest report. I reported it responsibly by email instead.

They revoked the token immediately.
