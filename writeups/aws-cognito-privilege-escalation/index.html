Super Admin privilege escalation from a misconfigured AWS Cognito

May 12, 20223 min read#pentest#aws#privesc

The scope of work and its details are redacted under the rules of engagement.

Introduction

The web application was an exam portal where faculty can create and schedule online exams, then invite and assign tests to students. Students log in and take their exams.

The portal did not let users update any of their own details. Any change had to be requested from the admins.

AWS Cognito

I intercepted the login request and noticed the unusual headers X-Amz-Cf-Pop and X-Amz-Cf-Id. A quick search showed that AWS Cognito was handling authentication.

Some background on how AWS Cognito works:

  1. To log in to the application, Cognito's login page is presented.
  2. On login, the credentials are checked against the user pool.
  3. If they're valid, the server returns JWTs, which are then used to talk to the application.
HTTP/2 200 OK
[...]
{
  "AuthenticationResult": {
    "AccessToken": "[REDACTED]",
    "ExpiresIn": 3600,
    "IdToken": "[REDACTED]",
    "RefreshToken": "[REDACTED]",
    "TokenType": "Bearer"
  },
  "ChallengeParameters": {}
}

So the login flow in the app I was testing was:

  • Log in to the app, which sends a POST request to Amazon Cognito.
  • If the credentials are valid, Cognito returns the tokens.

Exploitation

Having worked with AWS before, I knew this token could be used with awscli. That let me fetch my user's information from the user pool:

aws --no-verify-ssl cognito-idp get-user \
  --region <[redacted]> --access-token <[redacted]>

...
  "Username": "[redacted]",
  "UserAttributes": [
    { "Name": "sub",            "Value": "[redacted]" },
    { "Name": "email_verified", "Value": "true" },
    { "Name": "name",           "Value": "[redacted]" },
    { "Name": "email",          "Value": "[redacted]" },
    { "Name": "custom:userid",  "Value": "[redacted]" }
  ]
}

User attributes can be changed with update-user-attributes. Changing the email and name fields didn't work. Then custom:userid caught my eye, and changing it did.

@_@

I logged in as a different user, took their custom:userid, and set it on my own user. The update went through, and when I logged in again I had all of that user's privileges.

*_*

The last piece was the Super Admin's userid. I got it from the unauthenticated API data leak I found in the same engagement.

After setting the Super Admin's userid on my user, my privileges were escalated to Super Admin.

\ (•◡•) /

Threat and impact

It was a three-day, time-boxed engagement, so I wrapped up at the privilege escalation and didn't push it further toward remote code execution from the admin panel.

Even so, it could be chained with social engineering to trick faculty, students and other users. The possibilities are endless once you're a Super Admin.

Mitigation

  • Remove sensitive details from server responses, including the Cognito Identity Pool ID. Servers should return the minimum data needed.
  • Create an AWS policy that stops regular users from writing or updating specific user attributes.
  • AWS docs: Identity-based policy examples for Amazon Cognito.
